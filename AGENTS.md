# AGENTS.md

## What this is

Linkbio by CodePath: a "link in bio" platform for Brazilian small businesses and agencies, a product of CodePath (https://codepath.dev.br). Production URL: `https://linkbio.dev.br` (customer pages at `/<slug>`); the company's own site is hosted in another project. Brand constants (`SITE_NAME`, `COMPANY_NAME`, `COMPANY_URL`, `SITE_HOST`) are in `src/lib/site.ts`. Product scope is in `docs/PRD.md`. Built with Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS v4 + PostgreSQL (via `pg`, raw SQL). The backend lives in this repo (`src/server/`); locally Postgres runs in Docker. All user-facing copy is Portuguese (pt-BR).

Follows the same conventions as the sibling site projects (`../site-moraex`, `../site_leticia_moraes`).

## Commands

- `npm run dev` — dev server (Turbopack)
- `npm run build` — production build
- `npm run start` — run the production build
- `npm run lint` — ESLint (flat config, `eslint-config-next`)
- `npm run db:up` — start local Postgres (docker-compose, port 5435)
- `npm run db:migrate` — apply pending `db/migrations/*.sql` to the local DB (`.env.local`). Tracked in `schema_migrations` (filename + sha256). Refuses to continue if an applied file's checksum changed.
- `npm run db:migrate:prod` — same, against production Neon (`.env.neon`). Use a direct URL (`DATABASE_URL_MIGRATIONS`, or a non-pooler `DATABASE_URL`).
- `npm run db:migrate:baseline` / `db:migrate:prod:baseline` — one-time: record migrations whose schema is already present, without executing them. Required once on production before the first automatic deploy. See `docs/MIGRATIONS.md`.
- Production Vercel builds run `node scripts/migrate.mjs` before `next build` only when `VERCEL_ENV=production` (`vercel.json` `buildCommand`). Preview and development exit without connecting. A migration failure fails the deploy, so the previous production deployment stays live. Local `npm run build` does not migrate.
- `npm run db:seed` — dev-only demo account + page + 30 days of events (credentials at the top of `scripts/seed.mjs`)
- `npm test` — Vitest unit tests (`test/*.test.ts`); DB tests are skipped
- `npm run test:e2e` — Playwright (Chromium) em `e2e/`: sobe `next dev` na porta 3100 contra o Postgres local (`npm run db:up`), aplica as migrações e recria a conta do seed. Recusa bancos que não sejam locais; e-mail, PostHog e cobrança ficam desligados. Primeira vez: `npx playwright install chromium`. Cobre cadastro (até a confirmação), login, edição no painel refletida na página pública e clique rastreado. Não cobre o checkout do Asaas nem o código de confirmação por e-mail.
- `npm run test:db` — also runs `test/*.db.test.ts` against the local Docker Postgres (via `TEST_DATABASE_URL`, never `.env.local`)

Env vars live in `.env.local` (see `.env.example`): `DATABASE_URL`, `APP_SECRET`, `NEXT_PUBLIC_SITE_URL`, optional `RESEND_API_KEY` + `MAIL_FROM` (signup confirmation code and password-reset e-mail; without them, in dev the e-mail is printed to the server terminal), and billing: `BILLING_ENABLED`, `ASAAS_API_URL`, `ASAAS_API_KEY` (starts with `$`: single-quote it in `.env` files), `ASAAS_WEBHOOK_TOKEN`, `CRON_SECRET`; optional `ADMIN_EMAILS` (comma-separated, who can open `/admin`), `FORMS_KEY_SECRET` (signs Formulários API keys; falls back to `APP_SECRET`) and `GOOGLE_SITE_VERIFICATION` (Search Console meta tag). `.env.local` uses the local Docker DB; the production `DATABASE_URL` lives only in `.env.neon` (used by `db:migrate:prod`) and in Vercel. Production migrations prefer `DATABASE_URL_MIGRATIONS` (direct Neon URL, Production build only — never Preview). Never put the Neon URL back in `.env.local`: `db:seed`, `next dev` and `next start` read it.

Unit tests live in `test/` (e2e in `e2e/`); `vitest.config.mts` aliases `@` to `src` and stubs `server-only`.

## Architecture

- **`src/app/layout.tsx`** — fonts (Bricolage Grotesque + Manrope via `next/font/google`), only the metadata common to every route (`metadataBase`, title template, default robots, `viewport.themeColor`, Search Console `verification.google` from `GOOGLE_SITE_VERIFICATION`), `@vercel/analytics` and `@vercel/speed-insights`. Metadata files: `sitemap.ts`, `robots.ts`, `opengraph-image.tsx` (site share image via `next/og`), `manifest.ts`, `apple-icon.tsx`, `icon.svg`; `not-found.tsx` is the branded 404.
- **SEO (`src/lib/seo.ts`)** — Next merges metadata **shallowly**: a page that sets `openGraph`/`twitter` replaces the layout's whole object, and one that doesn't inherits it. So the layout sets none and every indexable page builds both with `socialMetadata({ title, description, path })`. The product JSON-LD (`productJsonLd`: Organization + SoftwareApplication with offers + WebSite) and keywords live only on the home. User pages: `profileTitle` ("Nome (@slug)"), `profileDescription` (bio, else the first link titles), `profileJsonLd` (`ProfilePage` → `Organization`, `sameAs` from social links via `socialProfiles`), `[slug]/opengraph-image.tsx` (name, photo, theme colors; `sharp` converts the photo to PNG because `next/og` can't read WebP). **Indexing rule** `isIndexable` = `profiles.search_indexing` (user toggle "Aparecer no Google" on the Links tab) + name or bio + ≥ 1 active link; otherwise the page gets `noindex, follow` and stays out of the sitemap (`INDEXABLE_SQL` is the same rule in SQL — change both together). `sitemap.ts` is dynamic (home, `/demo`, `/formularios`, all indexable pages with `updated_at` and avatar image; one file up to 50k URLs). Link and appearance actions bump `profiles.updated_at`. `/Foo` 308-redirects to `/foo`. Inline JSON-LD goes through `jsonLdString` (escapes `<`). `/go` and `/api` send `X-Robots-Tag: noindex` (`next.config.ts`).
- **Static home** — `/` reads no cookies so it's prerendered; `Nav`/`FooterAccountLink` learn about the session in the browser via `useLoggedIn`, which reads the non-httpOnly `lb_logged=1` flag cookie (set with the session in `createSession`, cleared in `destroySession`, backfilled by `proxy.ts`). It's cosmetic only; never trust it for auth.
- **`src/app/page.tsx`** — marketing landing; only composes section components in order: `Nav`, `Hero`, `StatsBar`, `Recursos`, `ComoFunciona`, `Planos` (3 cards Grátis / Pro mensal / Pro anual, comparison table and FAQ, all derived from `src/lib/billing.ts`; with billing off it shows a "Lançamento" notice and every CTA says "Criar minha página"), `Cta`, `Footer`. Each section is a `<section id="...">` matching nav anchors (`#recursos`, `#como-funciona`, `#planos`, `#comecar`). Sections take no props and hold their own copy/data arrays.
- **App routes** — `[slug]` public page (ISR 60 s via `generateStaticParams` returning `[]`; dashboard actions call `revalidatePath`), `go/[id]` tracked redirect, `api/view` view tracking (posted by `ViewTracker`), `media/[id]` serves uploaded images from Postgres (immutable cache), `login` (email + password, `?modo=cadastro` for signup; `login/confirmar` is step 2 of signup — the 6-digit e-mail code, with resend and "usar outro e-mail"; `login/recuperar` requests a reset e-mail, `login/redefinir` sets the new password), `api/redefinir-senha` (reset link target: moves the token into the httpOnly `lb_reset` cookie and redirects, so it never stays in the URL), `dashboard` with tabs: Links (`page.tsx`), `aparencia` (client `AppearanceEditor` with live preview; its section composition is `AppearanceSections`, shared with the playground), `resultados` (analytics), `plano` (plan/billing page; 404 when billing is off). All mutations are Server Actions in `dashboard/actions.ts` and `login/actions.ts`. `api/asaas/webhook` receives Asaas events; `api/cron/billing` is the daily Vercel cron (`vercel.json`, auth `Bearer $CRON_SECRET`). `demo` is a client-only playground (`Playground`), an in-memory adapter over the same `LinksEditor`, `AppearanceSections`, `EditorShell`/`EditorGrid`, navigation and preview used by the dashboard — no DB, nothing saved; sample data and pure local link helpers are in `src/lib/playground.ts`, and images live in `public/demo/`. `admin` is the internal admin (layout + every page and action call `requireAdmin` from `src/server/admin.ts`: signed-in user whose e-mail is in `ADMIN_EMAILS`, parsed by `src/lib/admin.ts`; anyone else gets a 404): `/admin` summary (signups, plans, estimated MRR, revenue, recent invoices and signups), `/admin/contas` (all accounts, search `?q=`, 50 per page `?pagina=`), `/admin/contas/[id]` (account, page, links, subscription, invoices, 30-day stats) with the only write actions, set/remove `courtesy_until` (`admin/actions.ts`). Plans there are computed with `realPlan` (billing treated as on), so the real subscription state shows even with billing off. Admin queries are the one place that reads across all owners.
- **`src/server/`** (all `server-only`) — `db.ts` (pg Pool + `query`/`queryOne`), `auth.ts` (scrypt passwords, sessions table keyed by sha256 of an httpOnly cookie token, `requireUser` (redirects unverified accounts to `/login/confirmar`), single-use 1 h password-reset tokens that also drop all sessions and confirm the e-mail; e-mail confirmation codes: 6 digits, 30 min, 5 wrong guesses, stored as a hash in `email_verifications`; signup with an e-mail whose account was never confirmed reuses that account), `rate-limit.ts` (`auth_attempts` with hashed email/IP keys; rules in `RATE_RULES`; signin counts only failures), `mail.ts` (`sendMail` via Resend HTTP API, console fallback in dev), `media.ts` (image upload ≤ 2 MB, type sniffed from bytes, no SVG), `profiles.ts` (profile/link reads), `analytics.ts` (`trackEvent` with bot filter + dedupe + rate cap; `getStats`), `asaas.ts` (minimal Asaas v3 client via `fetch`: hosted checkout, cancel subscription, webhook envelope types), `billing.ts` (checkout/cancel, webhook ingest + idempotent event queue `billing_events` with claim/retry, invoice mirroring, grace expiry, `getPlan`). **There is no RLS: every query must filter by the owner's user id in code.**
- **`src/proxy.ts`** — only checks the session cookie exists for `/dashboard` and `/admin`; real validation happens in pages/actions via `requireUser`.
- **`src/lib/`** — `types.ts` (Profile/LinkItem/Appearance, button styles, fonts, theme presets), `validation.ts` (slug/URL/WhatsApp/color), `site.ts` (site URL/name from `NEXT_PUBLIC_SITE_URL`), `billing.ts` (pure billing rules: prices, free limits, `planState`, invoice status ranking, `applyPlanToLinks`).
- **Billing / paywall (Grátis + Pro)** — same design as the sibling Ambiento project: Asaas hosted checkout (recurring credit card, monthly R$ 9,90 or yearly R$ 70,80 = R$ 5,90/month; prices live only in `PRO_PRICES`), `externalReference = "linkbio:<userId>"` (events with another prefix belong to other products on the same Asaas account and are ignored). Only the webhook changes state; the checkout return (`?checkout=ok`) just polls (`AutoRefresh`). Plan state is **derived on read** by `planState` (active until `current_period_end` + 3 days tolerance; `canceled_at` = Pro until period end; `past_due` = Pro until `grace_ends_at`, 7 days; `courtesy_until` = manual free Pro). A new `SUBSCRIPTION_CREATED` cancels the previous live subscription at Asaas (cycle/card change never double-charges; checkouts while paid set `nextDueDate` to the paid-until date). Free limits are enforced server-side (`addLink` limit, layout forced/kept in `readLink`, 30/90-day stats) and at render (`toPageViewProps(profile, links, pro)` → first 5 links as buttons + "Feito com Linkbio"). With `BILLING_ENABLED` not `"true"`, everyone is Pro and billing routes 404.
- **Public page rendering** — `PageView` takes appearance as CSS variables (`--bio-bg`, `--bio-text`, `--btn-bg`, `--btn-text`) plus `bio-btn-*` / `bio-font-*` classes; the same component renders the public page, `/demo` and the dashboard `PhonePreview`. Each link has a `layout` (`button` with optional thumbnail, `featured` big image on top, `tile` square — consecutive tiles are grouped into a 2-column grid by `groupTiles`) and a `size` (`sm`/`md`/`lg`, `.bio-size-*`); edited via `LinkOptions` inside the shared `LinkFields` forms in both the dashboard and playground.
- **Analytics** — no IP or cookies stored; a daily visitor hash (`APP_SECRET` + day + profile + IP + UA) counts unique visitors and dedupes (view: 30 min, click: 30 s, max 120 events/visitor/hour). Source comes from in-app UA (Instagram/Facebook/TikTok…) or referrer host. Days are computed in `America/Sao_Paulo`. Chart colors are validated categorical slots `--series-1`/`--series-2`.
- **Formulários** — commercial page at `/formularios`, linked from the home and footer, presents the Pro feature and a launch notice when billing is off. Effective access is `getPlan(userId).pro || users.forms_enabled`: Pro (including when billing is off) grants access automatically; admin can grant/revoke the manual flag independently of plan and form creation. Revoking the flag does not block a Pro account; losing both access conditions blocks dashboard, public submissions and external keys without deleting data or changing keys. The dashboard builder publishes at `/<slug>/f/<form_slug>`; public submissions use `/api/forms/publico`, browser session storage and conservative version conflicts. External sites post server-to-server to `/api/forms/respostas` with a form key; never expose it in the browser. Owner-scoped queries and key derivation are in `src/server/forms.ts`. Partial responses inactive for 180 days can be pruned opportunistically or by authenticated `/api/cron/forms`, which still needs scheduling. See `docs/FORMULARIOS.md` for management, API, migrations, limitations, privacy and pending launch decisions.
- **`src/components/RevealWrapper.tsx`** — polymorphic scroll-in `.reveal` wrapper (`IntersectionObserver`), combine with `.d1`–`.d4` delay classes. `Hero`/`StatsBar` skip it so above-the-fold content shows immediately.
- **Painel (navegação e padrões de UI)** — `DashTabs` é o adaptador autenticado (rotas e telemetria) da barra visual `EditorTabs`, também usada pelo demo com seleção local: no computador, pílula que desliza até a aba ativa (aba marcada na hora do toque, antes da página chegar); em ≤ 900px vira barra inferior fixa com ícones (`.dash-nav`), e a prévia abre por um botão flutuante só com o ícone (`PreviewPanel`: some ao rolar para baixo; o CSS detecta `.dash-nav` para posicioná-lo acima da barra inferior no painel e no `/demo`, e também acima da barra "Não salvo" quando ela aparece). `dashboard/loading.tsx` é o esqueleto das abas (vale também para Resultados e Formulários). Aba Links: cada link é um `<details class="link-card">` recolhido, dentro do `SortableLinks` (reordena arrastando pela alça ou com as setas do teclado; pointer events, sem biblioteca; otimista, grava com `reorderLinks`, que recebe a lista de ids e ignora ids de outro dono) e "Novo link" é o `NewLinkSheet` (`<dialog>`, bottom sheet no celular; qualquer elemento com `data-new-link` o abre; fecha sozinho quando o envio termina). Aba Aparência: seções recolhíveis (`Section`: `defaultOpen` abre em qualquer tela, `desktopOpen` só ≥ 901px; com `id`, a escolha da pessoa fica no `localStorage` por tela, chave `lb:sec:<id>:d|m`; hoje Perfil, Tema, Botões e Fonte abrem no computador e só o Perfil no celular; seções que convidam ao Pro, como o Selo no Grátis, ficam sempre abertas, sem `id` e com `proTag`, para não esconder o upsell), redes sociais + perfil + aparência num único formulário/`updateAppearance` (o endereço continua separado, `updateSlug`), `AppearanceEditor` mostra a barra "Não salvo / Descartar / Salvar" comparando o estado com o último gravado (`version` = `profiles.updated_at`). O header do painel tem o link da página e o `SignOutButton` (confirma antes de sair; até 600px os dois viram só ícone, classe `hdr-btn`). Botões de envio usam `SubmitButton` (pending via `useFormStatus`) e avisos de sucesso/erro usam `Toast`. Animações respeitam `prefers-reduced-motion` (bloco no fim do `globals.css`). Evite `React.cache` nas leituras do usuário/perfil: Server Actions renderizam o destino do redirect na mesma requisição e leriam dado antigo.
- **Client components** — `Nav`, `FooterAccountLink`, `RevealWrapper`, `ViewTracker`, `DashTabs`, `AppearanceEditor`, `TrafficChart`, `AutoRefresh`, `AdminTabs`, `PasswordInput` (eye toggle), `SignupForm` (`useActionState` with `signUp`), `PreviewPanel` (wraps `PhonePreview`: sticky column on desktop; at ≤ 900px it leaves the flow and opens full-screen from the floating "Prévia" button), `ImageInput` (shrinks photos in the browser via `src/lib/shrink-image.ts` so uploads never exceed the Server Action `bodySizeLimit`). `src/app/error.tsx` replaces Next's black error screen with a reload prompt.
- **Fonte única dos editores (painel + demo)** — mudanças de layout/interação devem ser feitas em `EditorShell`/`EditorGrid` (estrutura), `EditorTabs` (navegação), `LinksEditor` → `LinkCard`/`LinkFields` + `NewLinkSheet`/`SortableLinks` (Links), e `AppearanceSections` → `AppearanceFields`/`Section` (Aparência, incluindo redes e selo). Não recrie cartões, seções ou campos no `Playground` nem nas páginas do painel. Dados/callbacks comuns: `src/lib/editor.ts`; componentes compartilhados não importam `src/server` nem Server Actions. O painel fornece ações reais e mantém autorização, limites, endereço, indexação, QR code e salvar/descartar; o demo fornece callbacks em memória, prévia imediata, restauração e gerenciamento de object URLs (revogadas ao trocar/remover/restaurar/desmontar). Eventos PostHog de mutações só são habilitados pelo adaptador do painel, nunca pelo demo. Novos controles comuns entram na composição compartilhada para aparecerem nos dois contextos automaticamente. Testes: `test/editor-parity.test.tsx` renderiza composições reais; `test/editor-interactions.test.tsx` usa React/DOM com jsdom (ambiente só desse arquivo) para trocar abas e comparar seções, editar/criar/excluir/reordenar, restaurar, liberar imagens e preservar salvar/descartar; `test/playground.test.ts` cobre os helpers locais. Rode `npm test` ao alterar esses componentes e confira desktop/mobile.
- **Styling** — plain global CSS in `src/app/globals.css`: CSS custom properties on `:root` (`--ink`, `--paper`, `--lime`, `--whats`, …) plus BEM-ish classes (`.wrap`, `.btn-*`, `.h2`, per-section `.hero-*`, `.feat-*`, `.dash-*`, `.bio-*`). Tailwind v4 is imported but not used for styling — don't add Tailwind utilities ad hoc. Responsive rules are hand-written `@media` blocks at the end (900px, 600px, 400px). On mobile, form `.field`s are 16px (smaller makes iOS Safari zoom in on focus); placeholders must not be the only label. Public page appearance is driven by `--bio-*`/`--btn-*` variables set inline by `PageView`.
- **Security headers** — set centrally in `next.config.ts`.
- **Database** — `scripts/migrate.mjs` applies `db/migrations/*.sql` in filename order, each in its own transaction, under a Postgres advisory lock. `schema_migrations` stores the filename and sha256; a changed file aborts the run before anything pending is applied. The production build does this only when `VERCEL_ENV=production`, using `DATABASE_URL_MIGRATIONS` (else `DATABASE_URL_UNPOOLED`, `POSTGRES_URL_NON_POOLING`, or a non-pooler `DATABASE_URL`). Connection strings are never logged. One-time production baseline and sentinel map (`SENTINELS` in `scripts/migrations.mjs`): `docs/MIGRATIONS.md`. Add schema changes as new numbered files, never edit applied ones. History: `db/migrations/0001_init.sql`: `users`, `sessions`, `media`, `profiles` (incl. appearance columns), `links` (incl. `thumbnail_id`), `events`; `0002_link_layout_size.sql` adds `links.layout` and `links.size`; `0003_auth_security.sql` adds `auth_attempts` and `password_resets`; `0004_billing.sql` adds `subscriptions`, `invoices`, `billing_events`; `0008_user_details.sql` adds `users.first_name`/`last_name`/`instagram` (signup); `0009_whatsapp_style.sql` adds `profiles.whatsapp_style` (`green`/`theme`/`custom`) + `whatsapp_color`/`whatsapp_text_color`; `0010_email_verification.sql` adds `users.email_verified_at` (existing accounts backfilled as confirmed), `email_verifications` and the `verify` rate-limit action; `0011_cover_image.sql` adds `profiles.cover_image_id`; `0012_search_indexing.sql` adds `profiles.search_indexing`; `0013_show_avatar.sql` adds `profiles.show_avatar`; `0014_forms.sql` adds `forms` and `form_responses`; `0015_form_builder.sql` adds builder fields and account access; `0016_public_response_version.sql` adds public response versioning. `0017_profile_socials.sql` adds `profiles.social_links`.
